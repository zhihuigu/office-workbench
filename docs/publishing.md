# 维护者发布步骤

无历史发布包不包含 Git 元数据、远端设置或个人 Git 配置，打包工具不会自行上传。不要将整个交付父目录发布；只有 office-workbench 源码目录属于候选。测试输出、评估报告和私人审阅资料放在源码外。

## 发布前

1. 阅读 THIRD_PARTY.md，确认新增内容的权属及署名，并保留项目的 MIT LICENSE；第三方内容单独遵守其授权。
2. 逐文件审阅 PUBLIC_FILES.txt 列出的内容，确认没有私人信息、业务示例、凭据或授权不清的素材。
3. 在没有全局包的环境运行 tests/run.py，在临时私人目录完成初始化与演示；按实际结果填写支持范围，不虚构 CI 或跨平台成绩。
4. 运行 `python -I -B tools/release.py check`。白名单拒绝额外文件，常见模式扫描不是万能保证。
5. 用 `python -I -B tools/release.py pack --output 外部不存在的候选.zip` 生成审阅包。它固定白名单和 ZIP 元信息，不带文件时间、用户名或旧 Git 历史。

## 首次 GitHub 上传

只在用户明确授权后进行。从审阅过的纯代码包解压到新目录，创建全新 Git 仓库，使用发布者自己确认的身份和仓库名；不要复用私有仓库 `.git`、remote、commit message 或对象数据库。

首次提交前审阅暂存区文件清单和 diff，核对没有运行数据。不要运行 `git add` 覆盖一个包含私人资料的父目录。之后再连接授权的远端并上传；本项目没有自动上传脚本。

release.py check 是无 Git 历史候选的严格检查，会拒绝 .git。已开发的 Git 仓库应先将当前批准的文件导出到一个无历史的独立候选目录，再扫描、打包；检查 Git 历史需要额外的历史审查，不能靠该命令宣称已洗净。

如曾把私人资料纳入 Git，即使当前文件已删除，历史也可能残留。停止发布，改从逐文件审阅的白名单重建全新候选，不把旧 `.git` 带过去；已公开凭据需另行撤销或轮换。
